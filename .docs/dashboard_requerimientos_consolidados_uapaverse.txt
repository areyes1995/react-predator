OBJETIVO
--------
Este archivo consolida los requerimientos del Dashboard encontrados en
ambos documentos y los convierte en una especificación práctica para
implementar el Dashboard sin perder funcionalidades documentadas.

- Lo que debe corregirse en la arquitectura propuesta.

2. ARQUITECTURA DE NAVEGACIÓN
============================================================

REGLA PRINCIPAL:

El Sidebar NO debe renderizar directamente el contenido de una página.

El Sidebar solamente debe navegar hacia la URL correspondiente.

Flujo:

    Sidebar
       |
       v
    Click en opción
       |
       v
    Cambio de URL
       |
       v
    Next.js App Router
       |
       v
    Página correspondiente
       |
       v
    Contenido del Dashboard

Ejemplo:

    Sidebar -> Users
            -> /dashboard-admin/users
            -> Router
            -> Users Page
            -> RecordTable + filtros

La página debe poder abrirse directamente mediante URL y funcionar
correctamente al recargar.

REQUERIMIENTOS:

- Mantener el layout del dashboard.
- Mantener Sidebar visible.
- Cambiar solamente el contenido principal según la ruta.
- Marcar la opción activa del Sidebar según pathname.
- No duplicar layouts.
- No crear un sistema de routing paralelo.
- Todas las rutas deben estar protegidas por rol/permisos.
- Evitar rutas inexistentes.
- Corregir redirecciones inconsistentes.

============================================================

El Dashboard Admin debe servir como centro de monitoreo de la
plataforma.

Debe visualizar métricas e indicadores relacionados con:

- Visitantes.
- Proyectos consultados.
- Stands consultados.
- Intereses manifestados.
- Interacciones con avatares inteligentes.
- Preguntas realizadas a los avatares.
- Preguntas frecuentes.
- Solicitudes de contacto.
- Actividad general.
- Participación en ferias.
- Participación en salas.
- Proyectos/stands con mayor interacción.

Las métricas deben alimentarse de datos reales, no de mocks.

El documento identifica que actualmente las estadísticas y parte de la
actividad del Dashboard Admin todavía utilizan datos simulados.

10. USERS — NAVEGACIÓN
============================================================

La opción Users del Sidebar debe comportarse de esta manera:

    Click Users
        ->
    URL de Users
        ->
    Router
        ->
    Users Page
        ->
    RecordTable
        +
    RecordTable Filter

IMPORTANTE:

No colocar el RecordTable dentro del Sidebar.

No hacer que el Sidebar controle el contenido.

La URL es la fuente de verdad para decidir qué página se muestra.

La página Users debe funcionar también cuando el usuario accede
directamente a su URL.

37. CRITERIOS DE ACEPTACIÓN GENERALES DEL DASHBOARD
============================================================

1. El usuario solamente puede acceder al dashboard autorizado para
   su rol.

2. Una URL directa no debe permitir acceso no autorizado.

3. Al hacer click en una opción del Sidebar debe cambiar la URL.

4. El Router debe determinar qué contenido se muestra.

5. El contenido no debe ser controlado directamente por el Sidebar.

6. La página Users debe funcionar al acceder directamente a su URL.

7. Users debe utilizar RecordTable existente.

8. Users debe utilizar el filtro existente.

9. Los usuarios deben cargarse desde Backend.

10. Los roles deben poder actualizarse desde el Dashboard Admin.

11. Los stands deben cargarse desde Backend.

12. Los stands deben poder aprobarse.

13. Los stands deben poder editarse.

14. Los stands deben poder eliminarse.

15. Las métricas deben utilizar datos reales.

16. El expositor solo puede ver métricas de sus propios proyectos.

17. El administrador puede ver métricas generales.

18. Las preguntas de los avatares deben quedar registradas.

19. Deben poder identificarse preguntas frecuentes.

20. Los reportes deben poder filtrarse.

21. Los reportes deben poder exportarse.

22. Los intereses deben persistir.

23. Las solicitudes de contacto deben persistir.

24. Los mensajes deben persistir.

25. Las notificaciones deben persistir.

26. Las ferias y salas deben poder administrarse.

27. No deben existir mocks en los procesos principales.

28. Debe existir manejo de loading, empty y error states.

29. Debe funcionar responsive.

30. Debe pasar lint, type-check y build.

39. RESULTADO FINAL ESPERADO
============================================================

El Dashboard de UAPAverse debe convertirse en una plataforma
administrativa y de seguimiento completamente conectada al Backend.

Debe permitir:

ADMIN:
    Administrar usuarios, roles, proyectos, stands, ferias y salas;
    consultar métricas globales; revisar preguntas e interacciones;
    administrar notificaciones y generar reportes.

EXPOSITOR:
    Administrar sus proyectos/stands; consultar solicitudes,
    mensajes y métricas únicamente de sus propios proyectos.

EMPRESARIAL:
    Disponer de su dashboard funcional y conectado a la navegación,
    con las funcionalidades correspondientes al perfil empresarial.

INVITADO:
    Consultar sus intereses, historial y configuración.

Toda la navegación debe estar basada en URL + App Router.

El Sidebar navega.
El Router decide.
La Page renderiza.
Los componentes presentan la información.
Los servicios consumen el Backend.
Los permisos controlan el acceso.
Los datos reales alimentan el Dashboard.

NO debe existir dependencia de mocks para los procesos principales.
